# implement — handoff summary

# What I did

Took the six red acceptance scenarios to green by TDD, in the plan's phase
order F1 -> F2 -> F3 -> F4. Every increment was a unit test first, watched
fail, then the minimal code, then the acceptance run as the regression lock.

## F1 — Restoring a skip (AC-8, 3 reds)

`services/planned.py` gained `restore_payment(session, tx_id)`: `skipped ->
planned`, with the row's `RecurringOccurrence` returned to `planned` in the
same commit. `IllegalTransition` for anything not `skipped`, `NotFound` for
what does not exist, no balance movement, and `confirm_payment` still the
only door to `posted`.

`skip_payment` and `restore_payment` are now two calls into one private
`_move_status` helper, since they are exact inverses — one place decides how
a transaction and its occurrence move together. The duplicated occurrence
lookup in `_sync_occurrence_posted` was folded into the same `_occurrence_of`
helper. That is the extent of the refactoring; see "What I did not do".

Surfaces: `POST /planned/{tx_id}/restore` and the MCP tool `restore_payment`,
classified `WRITE_DESTRUCTIVE` alongside `skip_payment`, so the assistant
cannot restore on its own initiative.

## F2 — The queue carries only obligations (AC-15, 2 reds)

`services.planned.to_pay` now passes both buckets through `_obligations`,
which keeps expenses and transfers and drops planned income. Filtered in
Python over the two existing queries, exactly as the plan specified — no
change to `list_transactions`, no new SQL, no extra round trip.

I traced the third consumer the plan flagged: `services/reports.py`
`_pending_lines` builds from `to_pay`, so the monthly report stopped counting
planned income as pending without any edit — the coherent outcome, and now
locked by a unit test. `safe_to_spend` was confirmed untouched: it reads
`agg.month_planned_expense`, a different and already expense-only path.

## F3 — Combined total in the chat answer (AC-24, 1 red)

`mcp/format.to_pay_table` keeps its per-section subtotals and appends a
closing `**Total to pay (COP): …** · N item(s)` line **only when both
sections are present**. A single-section answer is byte-identical to before,
asserted directly on the last line of the output rather than by substring.

## F4 — Frontend

`RowAction` gained an optional `show?: (row) => boolean` predicate and
`DataTable` filters each row's menu through it — the generic mechanism the
surface needed, additive and backwards-compatible with every other page.
The transaction list uses it for a "Restaurar" action on skipped rows, wired
to `restorePlanned` in `lib/api/planned.ts` with the `transactionWrite`
invalidation group. "Por pagar" is untouched, per Angelo's decision.

Colocated vitest covers all three states: Restaurar appears on a skipped row
and calls the API with that row's id, and is absent on planned and posted
rows.

tool necessarily changes.** `test_temporal.py` asserted nine temporal tools,
`test_builder.py` enumerated every registered tool by name, and
`test_tool_tiers.py` enumerated every classified name. All three were updated
to include `restore_payment` — these are unit tests that inventory the tool
registry, not acceptance artifacts, so extending the inventory is the correct
response to adding a tool.

tests and `acceptance/handlers/planned_payments.py` are exactly as CP3 left
them. The handler's `planned.restore_payment` binding was already correct and
went green the moment the service function existed.

`domain/planned.py` is untouched: what enters the buckets stayed a decision of
the construction site.

## What I did not do

change I made is the `_move_status` / `_occurrence_of` extraction in F1, which
existed to avoid shipping a copy-paste inverse of `skip_payment`. Candidates I
noticed and left alone:

- `to_pay` is long and mixes window arithmetic, two queries and the filter;

- `to_pay_table`'s section assembly and the new total line both compute over
  the same items; there is a small duplication between `_to_pay_rows`'s
  subtotal and `queue.total_cop_cents`.
- The three MCP inventory tests list tool names by hand in three places.
