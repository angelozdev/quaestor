## 2. The MCP tool-inventory triplication — the refiner's caution was right on process, wrong on the risk

I verified the mechanism independently rather than taking the refiner's word:
13 `*_TOOL_NAMES` group tuples, union of **53** unique names, no duplicates;
`test_tool_tiers.py`'s hand-maintained `_KNOWN_TOOL_NAMES` also has **53**, with
**zero** difference in either direction today; `test_registry.py` already derives
from those tuples in **44 references across 11 constants**. So the refactor is
mechanically sound and the lists are currently in sync.

**Was the refiner right not to apply it? Yes — but for a different reason than
the one it gave.** Correct call on bounds: CP6's mandate is structure, naming and
duplication with no behaviour change, and changing what the test suite
*guarantees* sits outside that. Declining was right.

**But the specific risk it named does not exist.** The refiner rejected it
because the change "touches the ADR-0020 tier guard that keeps `restore_payment`
out of `LLM_ALLOWED_TOOLS`" and "could silently weaken that guard". I grepped:
**`_WRITE_DESTRUCTIVE_TOOLS` is referenced only from `tests/mcp/test_tool_tiers.py`
— `src/` never reads it.** The production guard is `LLM_ALLOWED_TOOLS`, an
explicit allowlist union of read + write-safe, plus `tool_tier()`'s
deny-by-default fallback. No test-side derivation can add a name to that
allowlist. The refactor cannot weaken the runtime boundary; it can only change
which *test* fails when someone forgets something.

**And in that dimension it strictly strengthens.**
`test_every_known_tool_is_in_some_tier_set` documents its own purpose as
catching "someone adds a new tool to the registry without classifying it" —
but because `_KNOWN_TOOL_NAMES` is itself hand-maintained, a developer who adds
a tool and forgets to classify it also forgets to list it, and the test passes
**vacuously**. That is a latent defect in the guard, predating this feature.
Deriving the list from the registry tuples is exactly what makes it non-vacuous.

**Is it worth an ADR? My read: no — but it is worth its own change.**
`CLAUDE.md`'s "testing strategy" clause aims at strategy-level decisions (which
layers we test, which frameworks, what the pipeline is), not at repairing one
test's vacuity. Deriving a test constant from the module under test sets no new
strategy here: `test_registry.py` established that precedent 44 times in the
same directory. Requiring an ADR to *follow* an existing in-repo precedent
inverts the rule's purpose.

What it should not be is part of feature 006. It touches security-adjacent tier
tests and fixes a defect that predates this branch; bundling it into a
planned-payments diff would bury a change to the LLM-reachability guard inside
an unrelated review surface. **Recommendation: file it as its own consolidation
item under rows 11-12 (`mcp-tool-surface` / `mcp-tool-tier-policy`), where it
belongs.** If Angelo wants the changed guarantee on the record, a two-line note
appended to ADR-0020 is the cheaper instrument than a new ADR.

## 3. `plan.md` lines 150-151 — the claim is false; amend the plan, not the code

**Verified myself: the refiner is right.** `plan.md` states the combined total
"se calcula sobre las filas ya convertidas, **sin segunda pasada de conversión**".
It does re-convert. `domain/planned.py:35-39` `total_cop_cents()` calls
`all_items()` and runs `to_cop_cents` over every row, while `format.py`'s
`_to_pay_rows` has already converted each row inside its own section. And
`api/routers/planned.py:21-23` does the identical double pass —
`TransactionOut.from_txs` converts per row, then `total_cop_cents(trm)` converts
again.

**Decision: amend the budget line in `plan.md`. Do not change the code.**
Reasoning, in order of weight:

1. **The double pass is the price of the parity guarantee, and parity is the
   point of AC-24.** `queue.total_cop_cents(trm)` is the single shared method
   that makes the chat answer and the screen headline report the same figure
   (ADR-0006/0009). Optimising only the MCP side would give the two surfaces two
   different routes to one number — exactly the drift AC-24 exists to eliminate.
   Trading a correctness guarantee for microseconds is the wrong trade.
2. **The alternative makes `format.py` worse.** Threading a precomputed subtotal
   out of `_to_pay_rows` means either changing it to return `(str, int)` —
   coupling a row renderer to totalling — or duplicating the conversion.
3. **The cost is noise at the stated scale.** `plan.md` itself says tens of
   rows, and `to_cop_cents` short-circuits COP to a plain int, so only USD rows
   do `Decimal` work.
4. **The budgets are explicitly informative.** `plan.md`'s own preamble: "(Autonomía
   medium — informativos, no gate.)" This is a descriptive line that described
   the wrong thing.

Proposed replacement for lines 150-151, in the artifact's language — **not
applied; `plan.md` is an approved CP4 artifact and amending it is Angelo's
call**:

```
- `to_pay_table`: el total combinado reutiliza
  `OutstandingQueue.total_cop_cents`, el mismo método que usa el router REST.
  Eso implica una segunda pasada de conversión sobre las filas que cada sección
  ya convirtió — coste despreciable a esta escala (decenas de filas, y
  `to_cop_cents` corta en COP sin tocar Decimal) y es justamente lo que
  garantiza que el chat y la pantalla reporten la misma cifra
```

# Other findings carried forward

per their docstrings. I do **not** think this belongs in ADR-0034 as the refiner
suggested — 0034 is about the reversibility of a skip, and the divergence comes
from AC-15. It is a product-semantics note; `docs/decisions/product-decisions.md`
is the right home if it is recorded at all.
