## What I did

Read all 59 scenarios in `spec.md` against `acs.md` (24 ACs), `feature.md`,
`CLAUDE.md` and `.engineer/manifest.yml`, then audited each one on three axes:
implementation leakage, one behaviour per scenario, and clarity/portability. I
also ran a mechanical grep for the classic leakage markers and cross-read
`acceptance/handlers/planned_payments.py` to test whether the spec's wording
stands on its own or leans on the handlers. I modified nothing.

## A — Implementation leakage: none

No scenario contains a class, function or method name, a table, column or
query, an endpoint, HTTP verb or status code, a framework term
(controller/service/repository/middleware/session), an internal data structure
or a file path. The vocabulary that does appear — planned payment, overdue,
upcoming, outstanding, confirm, skip, restore, due date, payee, account,
balance, TRM, COP, transfer, monthly obligation — is the user's own.

Two constructs deserve explicit credit, because they are exactly where leakage
usually enters:

- `spec.md:141` — `And "Bancolombia" is the account transfers come from`
  instead of naming the default-source-account setting.
- `spec.md:174` — `this month's turn of the obligation to "Acueducto" is marked
  skipped` instead of naming the recurring occurrence record.

### Informational — the preamble, outside every Gherkin block

Not scenario content, so not counted as violations, but stated for the record:

- `spec.md:3` — ``Formalizes `acs.md` (24 ACs, approved 2026-08-01) as standard
  Gherkin.`` — a repository artifact name inside the contract document.
- `spec.md:11-12` — `describe decided target behaviour and are expected RED /
  against current code (ATDD red phase).` — test-process vocabulary.

Rewrite, if the preamble is ever tightened: describe the two behaviours as
"decided but not yet built" and drop the artifact name and the RED/ATDD terms;
that history belongs in the handoffs, which already carry it.

## B — Borderline internal vocabulary (4)

**B-1 · `spec.md:146`**
`  And the transfer into "Ahorros" is recorded as one movement out and one movement in`
This states the ledger's two-row shape rather than what the user sees. It is
defensible — the user really does see two entries — but it is the closest the
spec comes to describing storage.
Rewrite: `And the transfer into "Ahorros" shows as money leaving "Bancolombia"
and money arriving in "Ahorros"`.

**B-2 · `spec.md:241`**
`  When the obligations that have come due are raised again`
Passive, no actor, and it names an internal batch run rather than anything the
user does or witnesses. A reader cannot tell what event triggers it.
Rewrite: `When the app next looks for obligations that have fallen due`.

**B-3 · `spec.md:479` (and `spec.md:488`)**
`  And the savings contribution that follows a confirmation cannot be recorded`
This is fault injection expressed as a precondition, and it encodes the order
of an internal chain ("that follows a confirmation"). Acceptable for an
all-or-nothing AC, but it is the one Given a different implementation could not
satisfy without knowing that a post-confirm step exists.
Rewrite: `And the savings goal this payment feeds cannot be updated`.

**B-4 · `spec.md:352`**
`  Then the request is rejected as an impossible period`
"Request" is transport-adjacent vocabulary, and the step never says what the
user perceives — AC-16 promises "a clear message".
Rewrite: `Then the user is told the period is impossible`. The same reading
applies to the bare `Then the plan is rejected` (`spec.md:361, 372, 377, 382,
388`) and `Then the confirmation is rejected` (`spec.md:423, 433, 443, 481,
490`) — see F-5.

## C — Hidden precondition, and a contradiction it creates (1 finding, 8 scenarios)

**C-1 · the exchange-rate precondition is silent in 8 scenarios that read the
outstanding list.**

AC-20 (`spec.md:450-456`) says the outstanding list is withheld until a rate
exists:

```
Scenario: The outstanding list is withheld until a rate exists
  Given no TRM has been set
  ...
  Then the outstanding list is not shown
  And the user is told to set the TRM
```

Yet these eight scenarios assert content in the outstanding list without any
rate in their preconditions:

| Line | Step |
| --- | --- |
| `spec.md:25` | `And the outstanding list for the next 30 days shows "Taller" as upcoming` |
| `spec.md:82` | `Then the outstanding list for the next 7 days does not show "Tigo"` |
| `spec.md:88` | `Then the outstanding list for the next 7 days does not show "Tigo"` |
| `spec.md:119` | `And the outstanding list for the next 7 days does not show "Enel"` |
| `spec.md:167` | `And the outstanding list for the next 7 days does not show "Gimnasio"` |
| `spec.md:186` | `Then the outstanding list for the next 7 days shows "Claro" as upcoming` |
| `spec.md:362` | `And the outstanding list for the next 7 days is empty` |
| `spec.md:542` | `Then the outstanding list for the next 7 days shows "Claro" as upcoming` |

Read in plain domain language by someone reimplementing this feature from the
spec alone, those eight contradict AC-20: the list is being read with no rate
established, and it answers.

They pass today because the two phrasings bind to two different code paths —
`acceptance/handlers/planned_payments.py:100` (`_compute_queue`, docstring
"with no exchange-rate lookup") versus
`acceptance/handlers/planned_payments.py:121` (`_view`, "the rate is fetched
first and fails loud"). That distinction is invisible in the spec's words. The
prior handoff records the same symptom being fixed for thirteen scenarios by
adding `Given the TRM is 4100.00`; the eight above were resolved on the handler
side instead, which is where the coupling entered.

This is a portability finding, not a correctness one: the shipped behaviour is
right and the tests are green. But the spec is the contract, and today its
meaning depends on which phrasing was used rather than on what it says.

Rewrite (needs Angelo's permission — I did not apply it): put a feature-level
background immediately under `Feature:` at `spec.md:15`

```gherkin
Background:
  Given the TRM is 4100.00
```

and let the four scenarios that genuinely test rate absence override it with
their existing `Given no TRM has been set` (`spec.md:34, 451, 459, 466`). Every
list read then declares its own precondition, the ~20 repeated
`Given the TRM is 4100.00` lines collapse, and the two step phrasings become
interchangeable in meaning as well as in wording.

## D — More than one behaviour per scenario (2)

**D-1 · `spec.md:21-25`** — `Scenario: Planning a payment leaves the balance
untouched` asserts the untouched balance *and* that the payment appears as
upcoming. Both belong to AC-1, but the name promises only the first.
Rewrite: rename to `Scenario: Planning records what is owed without moving
money`, which covers both assertions honestly.

**D-2 · `spec.md:138-146`** — `Scenario: Confirming a proposed savings
contribution moves both accounts` asserts the two balances and then, at line
146, the shape of the resulting record. The third assertion is a different
behaviour from the one the name states.
Rewrite: keep lines 144-145 in this scenario and move line 146 into its own,
e.g. `Scenario: A confirmed contribution shows on both accounts`.

The other multi-`Then` scenarios (AC-19's and AC-21's rejections, AC-15's
exclusion, AC-23's read-time rate) assert one action's full observable effect
and are correctly single-behaviour.

## E — Clarity to a non-developer (5)

**E-1 · `spec.md:172` (recurs at 214, 223, 233, 239, 487)**
`  And a monthly obligation of 50000.00 COP to "Acueducto" from "Bancolombia" that the user approves by hand, already due`
Two configuration facts crammed behind a comma splice; "approves by hand" reads
as jargon.
Rewrite: `And a monthly bill of 50000.00 COP to "Acueducto" from "Bancolombia"
that the user approves each month, with this month's already due`.

**E-2 · `spec.md:258`**
`  And a planned payment of 45000.00 COP to "Netflix" from "Bancolombia" that fell due 1 days ago`
"1 days ago" is ungrammatical, and this is the scenario that pins the
overdue boundary — the one place the wording must be unambiguous.
Rewrite: `... that fell due yesterday` (mirrors `due today` at line 251).

**E-3 · `spec.md:287` (and 294)**
`  And a planned payment of 100000.00 COP to "Deuda vieja" from "Bancolombia" that fell due in a month before last`
"in a month before last" reads as "some month prior to last" rather than the
specific month.
Rewrite: `... that fell due in the month before last`.

**E-4 · `spec.md:411`**
`  And a recorded expense of 50000.00 COP tagged "mercado"`
"Tagged" introduces a concept the rest of the spec does not use — everywhere
else the word is `category` (lines 29-31, 386-387).
Rewrite: `And an expense of 50000.00 COP already recorded in category
"Mercado"`.

**E-5 · the coined noun "turn"** (`spec.md:174, 235, 237, 491`)
`this month's turn of the obligation` is a deliberate and successful dodge of
"occurrence", but it is never defined and a reader meets it cold.
Rewrite: either say `this month's bill for "Acueducto"`, or add one line to the
preamble — "a monthly obligation's *turn* is that month's instance of it".

## F — AC coverage gaps (5)

Each is a clause in an approved AC with no scenario asserting it.

**F-1 · AC-17, unsupported currency.** `acs.md:198-199` refuses a payment "in an
unsupported currency"; the AC-17 block (`spec.md:355-389`) covers zero/negative,
missing account, archived account, archived category and account-currency
mismatch, but never a currency the app does not support at all.

**F-2 · AC-19, source equals destination.** `acs.md:219` refuses a transfer
"when source and destination are the same account"; the AC-19 block
(`spec.md:416-445`) covers the missing source account, the zero amount and the
currency mismatch only.

**F-3 · AC-18, resolving something already skipped.** `acs.md:208` names three
states — "already confirmed, already skipped, or never owed". `spec.md:394` and
`spec.md:402` both start from an already-confirmed payment; `spec.md:409` covers
"never owed". The already-skipped case is unasserted, and it is the one that
now interacts with AC-8's restore.

**F-4 · AC-8, what survives a restore.** `acs.md:114-115` requires the restored
payment to keep "payee, amount, due date and account intact"; `spec.md:187`
asserts amount and due date, the payee only implicitly by reference, and never
the account.

**F-5 · AC-16/AC-17/AC-19, the refusal message.** `acs.md:200-201` — "Each
refusal names what is wrong" — and `acs.md:190-191` — "refused with a clear
message". Every refusal in the spec is asserted as a bare `the plan is rejected`
/ `the confirmation is rejected` / `the request is rejected`, so the promise
that the user learns *why* is never checked. Also worth noting: only the
Scenario Outline (`spec.md:362`) asserts AC-17's "nothing is recorded"; the four
other planning refusals do not.

Rewrite for all five: add one scenario each in the AC's own section, in the
existing style, and for F-5 extend the refusal steps to name the cause, e.g.
`Then the payment is not planned and the user is told the amount must be
positive`.

## Observations, not findings

- **Deliberate redundancy is fine.** `spec.md:78-88` re-asserts confirm/skip
  removal that AC-5, AC-7 and AC-22 also cover. That is the AC-per-section
  structure doing its job, not duplication to prune.
- **`TRM` is domain, not leakage.** It is the Colombian official rate and the
  user's own word; it stays.
- **Amounts and relative dates are portable.** Plain decimals and
  "in N days" / "N days ago" keep the boundary scenarios honest against a moving
  today, exactly as the preamble claims.
- **59 scenarios, 60 executions** — 58 `Scenario` plus one `Scenario Outline`
  with two examples. Matches the CP3 handoff.
