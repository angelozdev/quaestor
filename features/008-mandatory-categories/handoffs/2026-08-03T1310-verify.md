# verify — handoff summary

Mine, first-hand. The previous CP6 and CP7 were the implementer's work and the

feature 008 and I read its documents as claims to test.

## Verdict

**Yes.** Feature 008 meets its 19 acceptance criteria, and the two Principle 7
gaps are closed — CP6 no longer carries the implementer's signature, and
8cd0662 has now had the independent pass it never had.

That pass was worth running. It found two defects.

## R1 — the assistant's restore was inert, and N7's guard never fired there

`_resolve_category_by_name` in `backend/src/quaestor/mcp/tools/core.py` called
`categories.list_categories(session)`, whose `include_archived` defaults to
`False`. Every MCP category tool resolves through it, including the one whose
entire job is an archived category.

**Repro, through the assistant door:**

```
archive the expense category "Suscripciones"
restore_category(category="Suscripciones")
  -> "Category 'Suscripciones' not found. Pass it as new_category to create it
      while recording, or pick one from list_categories."
  -> row still archived
```

**The dead end.** AC-13 refuses a colliding create with *"an archived expense
category is already named 'Vuelos' — restore it instead of creating a second
one."* Taking that advice through the same door returned "not found". The app
told the owner to do something and then denied it — structurally the N1/N2
finding the owner already ruled on, rebuilt somewhere else.

**N7 at the MCP door.** On production's `🛡️ Auto Insurance` shape the resolver
saw only the active row, so `unarchive_category` received a category that was
not archived, fell straight past 8cd0662's new guard, and returned a success
card:

```
restore_category(category="Auto Insurance")
  -> "Category **Auto Insurance** (id=2, expense, group: (no group))"
  -> archived row untouched, still archived
```

Commit 8cd0662 says the guard is *"reachable from POST
/api/categories/{id}/restore and the MCP restore_category tool"*. It was
reachable from the first only.

**Why every gate was green.** AC-10's step handler
(`acceptance/handlers/mandatory_categories.py:618`) calls
`categories.unarchive_category` directly — the service, not a door. And the
only test over the MCP tool, `test_archive_and_restore_category_roundtrip`,
asserted `"Groceries" in out`; the NotFound message contains "Groceries", so it
passed on the error string. A false green sitting on top of a dead tool.

**Fix.** `allow_archived` on `_resolve_category_by_name`, passed by
`restore_category`, with an archived match preferred so a same-name pair
resolves to the row actually being restored. This is not a new pattern —
`_resolve_account_by_name` already had exactly it, and `masters.py:85` even
carries the note *"Include archived so restoring an archived account
resolves."* Categories were simply never given it. Blast radius is one call
site: the other three callers keep the default, where the new code path is
byte-equivalent to the old first-match-wins.

Four regression tests, all confirmed RED first, including a strengthened
roundtrip assertion so the false green cannot come back.

## R2 — the refusal named a category that does not exist

`unarchive_category` interpolated `cat.name` (the row being restored) where it
meant `live.name` (the row blocking it). Matching folds case, so the two can
differ:

```
archived "AUTO INSURANCE" + active "Auto Insurance"
POST /api/categories/1/restore
  -> 422 "an active expense category is already named 'AUTO INSURANCE' —
          rename one of the two before restoring this one"
```

No category is named that. The advice points at a name no list will show.
Fixed to `live.name`, with a test.

## R3 — the third overstatement

The implementer had already been caught twice (D5/N5, and N7's per-direction
justification). Here is a third, inside N7's own justification.

Commit 8cd0662, the previous refine handoff and the previous verify handoff all
state that in production's `🛡️ Auto Insurance` pair *"the archived row has the
lower id"*, and build the whole repro on it: `_by_name` returned the first row
in query order, therefore the archived one, therefore the wrong message.

Production says otherwise. Read-only against quaestor-db-1:

```
  ctid  | id |       name       | is_income | archived
--------+----+------------------+-----------+----------
 (0,33) | 33 | 🛡️ Auto Insurance | f         | f
 (0,34) | 34 | 🛡️ Auto Insurance | f         | t
```

The **active** row is id 33 and sorts first. An unordered scan returns it
first, so the pre-fix `_by_name` would have returned the active row and
produced the *correct* "already exists" message. The stated failure does not
reproduce on the dataset it is stated against.

The fix is still right, for a better reason than the one recorded:
`unarchive_category` had **no** duplicate guard at all, which is
order-independent, so `POST /api/categories/34/restore` on production would
have flipped the archived row live and produced two active `🛡️ Auto Insurance`
rows of the same direction. That is the real, reachable half. The `_by_name`
ordering half is a latent hazard — there is no `ORDER BY`, so Postgres may
return either row after any rewrite — not a live production bug.

I removed the same false sentence from `_by_name`'s docstring, where 8cd0662
had corrected it in acs.md and ADR-0042 but left it in the source, and removed
the three prohibited `#` comments that commit added (CLAUDE.md bans comments in
new and modified code; they are now docstring prose).
