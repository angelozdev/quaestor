# implement — handoff summary

## What I did

Implemented feature 008 against the approved specs, in the four phases
`plan.md` lays out, closing all 29 red acceptance scenarios and leaving the
whole suite at 246/246.

## Artifacts produced

93 files changed (5922 insertions, 498 deletions) across the branch's 008
range. The shape:

- **One new rule, one new resolver.** `domain/rules.py` gained
  `category_is_income_for`, a pure predicate that answers direction and refuses
  a transfer outright. `services/categories.py` gained `resolve_for_movement`,
  the single place that decides which category a movement carries.
- **One migration.** `0010` adds a type-discriminated CHECK on `transaction`
  and `NOT NULL` on `recurring_item.category_id`, behind a pre-flight guard
  that counts dirty rows and refuses rather than guessing.
- **Three doors made equal.** `new_category` reaches REST, MCP and the form
  alike; `GET /categories?is_income=` filters by direction; the frontend's
  `allowNullLabel="Sin categoría"` is gone, replaced by `CategoryField`.
- **Two ADRs** (0041, 0042), both `accepted`, plus the product-side amendment
  as § ADR-036.

## Findings

- **The check existed five times, identically.** Every write path carried its
  own copy, and the new rule would have added three more checks to each. They
  collapse into `resolve_for_movement`, which is why AC-11 (a transfer refuses
  a category) and AC-14 (the assistant obeys the same rule) needed no code of
  their own — the assistant already went through services.

- **The feature contradicted an accepted product decision.** ADR-024 had
  explicitly rejected forcing a category, on friction grounds. Rather than
  contradict it silently, § ADR-036 supersedes that one clause and states what
  survives: a category *without an envelope* is still unbudgeted spending
  (ADR-016 untouched); what disappears is money with no category at all.

- **A blanket NOT NULL would have destroyed the transfers.** All 39 production
  transfers are correctly uncategorised. The constraint has to discriminate by
  type, which is ADR-0041 — verified on scratch Postgres before production saw
  it.

- **The migration guard caught a bug in the test suite, not in the data.**
  Revision 0010's pre-flight counted 1383 uncategorised expenses in a file no
  test should have been reading: `tests/jobs/test_daily.py` set `QUAESTOR_DB`
  in a fixture, but `db.engine` is built at import time, so four tests had been
  writing to the developer's real on-disk `backend/quaestor.db`. Fixed here;
  the pattern is filed as C7 because it may repeat elsewhere.

- **The mutation figure is real but not reproducible.** 77/77 on the two
  opted-in modules — but only after correcting my own measurement: the first
  sweep ran backend unit tests alone and reported four survivors, all of which
  the acceptance suite killed. The mutator itself was built ad-hoc in a scratch
  directory and never committed, so nobody can re-derive the number. Filed as
  C11.
