## The defect — a fourth transfer creation path

CP6's audit table listed three creation paths. There are four:

| Path | Shape | Direction |
|---|---|---|
| `transactions.transfer()` | pair, one group | both legs set |
| `goals.goal_contribution()` | pair, one group | both legs set |
| `planned._materialize_planned_transfer()` | pair, one group | both legs set |
| **`goals.propose_goal_contributions()`** | **one `planned` leg, no group** | **none, by design** |

The fourth is correct: a proposal has no counterpart until it is confirmed.
The delete path was not. `delete_transaction` routed on `tx.type ==
TxType.transfer` alone, so the group-less proposal entered
`_delete_transfer_pair` and hit its NULL-group guard. Every goal accrues one
such row per period; the UI offers "Eliminar" on every row with no status
gate, so the user meets a `ValidationError` for an action the interface
promised.

**Fixed test-first.** Written and run red before any production edit:

- `test_delete_group_less_transfer_removes_the_row_and_keeps_the_balance`
  (parametrized `planned` / `skipped`)
- `test_delete_group_less_transfer_removes_its_tag_links`
- `test_proposed_contribution_can_be_deleted_without_moving_balances`
  (through the real `propose_goal_contributions` path)
- `test_skipped_contribution_can_be_deleted_without_moving_balances`
  (through `skip_payment`, the shape of row 1462)
- `test_delete_grouped_transfer_without_direction_still_fails_loud` — the
  one that was green from the start and had to stay green

`delete_transaction` now routes to the pair branch only when the leg carries
a `transfer_group_id`; everything else takes the single-row path, which
reverses a balance only when `status == posted`. The reversal itself moved
into `_delta_balance_of`, which picks `leg_delta_balance` for a transfer and
`delta_balance` otherwise — so a *posted* group-less transfer without a
direction still fails loud instead of guessing a sign.

Both guards kept: the grouped-leg missing-direction raise, and
`_delete_transfer_pair`'s NULL-group guard (unreachable from
`delete_transaction` now, but it is what prevents a direct call from
rendering `transfer_group_id IS NULL` and selecting every non-transfer row —
the exact bug CP6 fixed).

Frontend: the confirm dialog copy is now chosen by `deleteDescription()`
using the new `hasCounterpartLeg()` helper. A single-leg row reads
"Esta transferencia todavía no tiene contraparte: se eliminará solo este
movimiento y ningún saldo cambiará." The new test was proven red against the
old copy before the change landed.

3. **The acceptance runner's hidden `SESSION_SECRET` prerequisite is still
   open**, first reported in feature 005's CP7 handoff (finding 1). Today it
   bites `uv run pytest -q` rather than the runner: without direnv loading
   `backend/.env.local.sqlite`, backend collection dies with
   `RuntimeError: SESSION_SECRET must be set and ≥32 bytes` on `tests/api`
   and `tests/chat`. A fresh agent reads that as a code regression.
   Recommend a test-only default in `backend/tests/conftest.py`.

4. **Deleting a goal proposal is now re-proposable, and that is the right
   behavior.** `propose_goal_contributions` is idempotent per (goal, period)
   by looking for an existing transaction with that `goal_id` in the period;
   once the row is gone, the next `close_month` re-proposes it. No dangling
   reference is left behind — a `GoalContribution` is only created at confirm
   time, so a `planned`/`skipped` proposal has none. Recorded, not changed.

5. **ADR-0032 amended**, not contradicted. Its Decision text said "deletion
   of either leg loads the pair by group", written as if every transfer row
   had a group. A Checkpoint 7 amendment now records the fourth creation
   path and the refined routing predicate. The MCP module docstring
   (`mcp/tools/transactions.py`) was corrected from "a transfer leg" to
   "a grouped transfer leg" for the same reason. No new architecturally
   significant decision is implied — no schema change, no new dependency,
   no migration.

6. **`spec.md` needs no change.** AC-5 is about transfers that have two
   sides; a proposal is not one yet. The single-leg delete is pinned at the
   unit layer, where the shape actually lives. Flagged rather than changed,
   per the rule.
