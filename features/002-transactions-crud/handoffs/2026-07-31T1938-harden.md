`mutation-manifest.json`, so `dae_mutmap.py select` had no cache to consult and
the atdd-mutate custom-tool path applied: an AST harness built in the
scratchpad, mutating one site at a time and restoring the original after each
run. Beyond the standard operator set I added **boolean operand drop** — for
`a and b`, emit `a` alone and `b` alone — because that is the operator that can
recreate the exact CP7 defect.

The `delete_transaction` one deserves a note because my first attempt at it was
wrong. Dropping `tx.type == TxType.transfer` leaves `if tx.transfer_group_id is
not None`. My first test gave an expense a stray group id and asserted a
single-row delete — and the mutant still survived, because for a group of size
one both paths reverse the same single balance and delete the same single row.
The behaviours only diverge when the group holds more than one row. The test
that actually kills it puts the intruder expense **inside a real pair's group**
and asserts the pair survives.

**One equivalent mutant remains, proven not assumed.** `_record:72`

`record_expense(..., payee=None)` still stores `''`, because SQLAlchemy applies

when the attribute is `None` at INSERT. No input can distinguish the two forms.
The test stays regardless — it pins the contract even though it cannot kill the
mutant.

## B. Gap analysis

### B1. The migration auto-apply, twice — and the trigger nobody had named

`runbook.md` blamed "migrations re-run on every reload" and proposed disarming
auto-migration or dropping the bind mount. Reading the code, the picture is
sharper — there are **two** triggers:

1. `__main__.run_migrations()` — subprocess `alembic upgrade head`, once per
   container start. This is ADR-0026's wait-migrate-serve contract, kept in
   force by ADR-0030, and it is human-initiated by `just dev-prod`.
2. `api/__init__.py:35` `db.init_db(db.engine)` → `db.py:134`
   `_apply_migrations` → `db.py:114` `alembic_command.upgrade(cfg, "head")` —
   inside the FastAPI **lifespan**, so it runs on every application start.
   Uvicorn runs `reload=True, reload_dirs=["/app/src"]` over a `rw` bind mount,
   so it fires on **every file an agent writes under `backend/src`**.

Container logs settle it: the `alembic.runtime.migration` lines appear after
`WatchFiles detected changes … Reloading` and before `api: lifespan startup`,
which is line 35 executing before the log call on line 36.

Trigger 2 is the incident mechanism, and no ADR ever decided it existed — it is
`init_db` doing two jobs (apply migrations; seed and wire hooks) because tests
need the second. That matters for the fix: the runbook's "disarm
auto-migration" would have to edit `_apply_migrations`, which every test fixture
in the repo depends on, to solve a deployment problem.

**Proposal: ADR-0033 (status `proposed`, not accepted).** Primary fix is to stop
bind-mounting `backend/src` in the pg profile — that deletes trigger 2 against
production entirely, is compose-only, contradicts no accepted ADR, and losing
hot-reload against the real database is a feature. Secondary is a pre-flight
check that makes `just dev-prod` refuse to start while revisions are pending,
naming them and demanding a backup — that covers trigger 1, which is legitimate
but should never be silent. The env-gate option is written up and explicitly
**not** chosen, with the reason. Per instruction, `docker-compose.yml` and the
`justfile` were not touched.

**A live near-miss inside this checkpoint made the case for me.** My first
mutation run wrote mutated service files straight into the working tree. The
api container was up, `src` bind-mounted, and it reloaded on each write — and
because `RUN_ON_BOOT=1`, each reload ran the daily job **on mutated code**. I
killed it after 8 mutants. It reached the SQLite sandbox rather than the real
Postgres purely because the stack happened to be on the sqlite profile; the pg
container had already been removed by a profile switch (its volume,
`quaestor_quaestor_pg_data`, is intact at 64.0M — nothing was lost). Everything
after that ran in a throwaway `git worktree`, which is the right answer
generally: **any agent process that writes into `backend/src` while the stack is
up is executing that code in the app.** That generalises ADR-0033's driver
beyond migrations, and it argues that mutation testing should run in a worktree
on *every* profile, not just pg. Worth adding to the DAE mutation workflow.

### B2. Why the fourth transfer creation path went unseen

The path was never invisible — it was out of scope at every checkpoint that
could have caught it:

- **CP2 (ACs)** wrote AC-5 as "deleting *either side* of a transfer removes
  *both* movements". The AC encodes "every transfer is a pair" as a premise. A
  wrong premise in an AC propagates to every downstream artifact.
- **CP3 (spec)** wrote three scenarios, all faithful to that premise.
- **CP4 (plan)** described the pair branch in the same terms.
- **CP5** implemented `if tx.type == TxType.transfer` — a correct reading of the
  model it was given.
- **CP6 (refine)** reviewed **the branch diff**. `propose_goal_contributions`
  is not in the diff — this feature never touched it — so a diff-scoped review
  structurally cannot see it. CP6 asked exactly the right question ("which
  creation paths set the direction?") but answered it from the three paths it
  already knew rather than from `grep -rn "TxType.transfer" src/`, which
  returns four producers in services.
- **The runbook caught it.** `verify-backfill` recorded "Two `type='transfer'`
  rows WITHOUT `transfer_group_id` (ids 1462, 1545 — planned single-leg
  instances) … flagged for CP7". Contact with real data was the only thing that
  broke the premise, and it happened at migration time — after the ACs, the
  spec, the plan and the implementation had all been built on it.

Three concrete changes that would have surfaced it earlier:

1. **Query the shapes before writing the ACs, not at migration time.** One
   read-only query at CP2 — `SELECT status, transfer_group_id IS NULL, count(*)
   FROM "transaction" WHERE type='transfer' GROUP BY 1,2` — returns the two
   group-less rows and kills the "every transfer is a pair" premise before AC-5
   is drafted. The database was available the whole time and costs nothing to
   read.
2. **When a checkpoint introduces a column-wide invariant, audit producers, not
   the diff.** "Every transfer leg has a direction" is a claim about every
   writer of that column. The audit unit is `grep` over the type/column across
   `src/`, and the review scope has to widen past the diff. A diff-scoped
   reviewer has a structural blind spot for exactly this class.
3. **Interrogate universals in AC language at discovery time.** An AC that says
   "every X has two Y" should draw the counter-question "is there an X with one
   Y?". ATDD already asks this about status transitions; it should ask it about
   shape.
