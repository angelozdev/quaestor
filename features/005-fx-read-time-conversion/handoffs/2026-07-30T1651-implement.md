# implement — handoff summary

## What I did

Implemented ADR-0031 read-time FX conversion end to end, following
plan.md's phasing:

- **F1 — TRM core**: `Settings.usd_cop` (Numeric(18,6), nullable),
  `fx.set_trm`/`fx.get_trm` (unset raises `MissingRate` naming the TRM),
  `money.to_cop_cents` (COP identity; USD × TRM half-up to the cent) and
  `money.implied_rate` (received ÷ sent), unit-tested first.
- **F2 — snapshot cut**: dropped `Transaction.fx_rate`/`to_base` and the
  `FxRate` model; Alembic revision 0005 adds `settings.usd_cop`,
  pre-loads it from the most recent `fx_rate` row, then drops the two
  columns (batch mode for SQLite) and the `fx_rate` table; every
  `to_base` consumer rewritten to read-time conversion with exactly ONE
  `get_trm` per read path (verified: one settings query per request in
  the query-count tests). `month_aggregate`'s SQL `sum(to_base)` became
  a per-(bucket, currency) `sum(amount)` converted in Python.
  `register_expense/income` lost `fx_rate`; `_resolve_fx` deleted. REST:
  `cop_equivalent` computed at read; GET reads 409 without a TRM (AC-9,
  even all-COP data), writes succeed without one (AC-1, `cop_equivalent`
  null). `/fx` GET/POST are scalar. `jobs/daily.py` calls `set_trm`.
- **F3 — cross-currency transfers**: `transfer()` takes the sent amount
  plus optional `amount_received` (required cross-currency); each leg
  stores its own physical amount in its account's currency; balances
  move per leg; no rate stored; the "both accounts must use the transfer
  currency" validation removed; amounts > 0 and distinct accounts kept.
  REST `TransferIn` and MCP `TransferInput` updated (tool names/tiers
  unchanged, ADR-0020).
- **F4 — frontend**: create dialog lost the fxRate field (both tabs);
  transfer tab gains a conditional "Monto recibido" field with the live
  implied rate ("Tasa implícita: X (solo informativa)", extracted as
  `TransferReceivedField` for testability); transactions page shows an
  "Equivalente (COP)" column from `cop_equivalent`; settings page is a
  single editable "TRM actual" field, no date. Colocated vitest for the
  new component, `impliedRate`, and the settings schema.
- **F5 — closure**: adjusted exactly two thin wrappers in
  `acceptance/handlers/fx_read_time.py` (`_cop_equivalent_cents` now
  goes through `money.to_cop_cents` + `get_trm`; `_transfer_cross_currency`
  calls the real `transfer(..., amount_received=)`); full acceptance run
  green 26/26.

Test migration across the 3 backend streams (services/api/mcp) was
parallelized across three subagents under a strict no-weakening
contract; their work plus mine took the suite from 82 failing after the
cut to 698 green.

## Decisions taken within the plan's envelope

- REST writes return `cop_equivalent: null` when no TRM is set (writes
  must succeed per AC-1); all GET reads call `get_trm` unconditionally
  and 409 (AC-9). Helper `trm_or_none` lives in `api/deps.py`.
- `GoalContribution.amount` now stores the leg's physical amount
  (identical to before for COP, the only real case; the frozen COP
  conversion is gone by design). Flagging for the refiner/verifier.
- History aggregates (`spent_by_cat_month`) convert per-(month,
  category, currency) sums rather than per row — keeps the bounded
  read-path; sub-cent divergence from per-row conversion is possible in
  theory, not observable in any spec scenario.
- `scripts/cleanup_stale_planned.py` prints its COP total only when a
  TRM exists (script must not crash on a fresh DB).
