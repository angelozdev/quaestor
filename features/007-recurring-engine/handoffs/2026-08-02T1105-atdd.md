## Findings

- **Five bindings name APIs that do not exist.** `recurring.pending_dates`,
  `accept_pending_dates` and `decline_pending_dates` (AC-12) are called by name
  and raise a clear message until they exist. `materialize_due` is read for a
  `failures` attribute it does not carry (AC-24), and the movement's origin is
  read off `Source`, which has no engine value (AC-25). These are the intent,
  not the design — plan time owns the final shape and may rename them, at which
  point the handler follows.
- **AC-9 and AC-12 needed a spec-level distinction.** Both concern dates that
  have already passed, but they must behave differently: a catch-up after
  downtime charges unattended, while dates already behind at declaration are
  offered. The spec draws the line at *when the obligation was declared* — a
  `Given` obligation predates its start date, a `When the user declares …` one
  does not. This is stated in the spec preamble because it is a real rule, not
  a test artifact.
- **AC-8 is the one place with absolute dates.** The end-of-month clamp cannot
  be asserted against a moving today, so those two scenarios pin a fixed
  calendar (31 January 2026 → 28 February → 31 March; 29 February 2024 → 28
  February 2025 → 28 February 2026) and run the engine "as if it were" a given
  day. Both pass — the clamp is shipped and correct.
- **Three target ACs are partially green already**, which narrows the work:
  extending an end date, the broken obligation being picked up once fixed, and
  a hand-entered movement not claiming to be the engine's all pass today.
- **The 006 seam holds.** AC-4, AC-6 and AC-27 reuse feature 006's own queue
  steps, so the hand-off between the two features is asserted rather than
  assumed, and AC-27 is green — `restore_payment` already syncs the occurrence.
