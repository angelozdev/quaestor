  ACs are designed clean-room (product-first, without reading the service),
  then diffed against shipped behaviour, with every divergence resolved
  explicitly as fix-or-accept. This overrides the default reverse-engineer
  posture used in tasks 1 and 2, and it is binding on CP2.
- Scope confirmed with the user before writing: the item lifecycle, the
  cadence arithmetic, `materialize_due`, the auto/manual split, skip, and the
  three surfaces. Out: queue confirm (006, done), FX fetch and month close that
  share the daily job, budget consumption.
- `auto` mode is the only path in the product that posts a transaction and
  moves an account balance with no user action, which raises the cost of any
  undetected divergence — flagged in `feature.md` Notes.
- Four intake candidates for divergence recorded but deliberately not judged:
  `start_date` is editable and can retro-open passed dates; `end_date` never
  deactivates the item; an `auto` materialization leaves no user-visible trace;
  skipping an already-`posted` occurrence leaves the balance moved.
- `ADR-020` in the module docstrings is pre-DAE numbering for the temporal
  engine design, not `docs/adr/0020-security-hardening-…` — noted in
  `feature.md` so the AC pass does not chase the wrong document.
