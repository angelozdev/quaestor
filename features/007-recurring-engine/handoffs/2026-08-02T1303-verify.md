## Findings

### Suites

### D4 — verified clean, no changes needed

All-or-nothing holds under adversarial probing. Accepted 2 of 5 offered dates,
then archived the account and accepted the rest: balance unchanged, tx count
unchanged, all 3 remaining dates still `offered`. The single commit interacts
correctly with row reuse — the occurrence count stays equal to the due-date
count with no duplicates or orphans, and a retry after fixing the account
accepts all 4 cleanly against the same rows. The scoping argument in the
docstring is right: per-charge commit exists for an unattended batch, and this
is one obligation with the user watching one button.

### D2 — right policy, wrong measurement, twice

The cap itself is well placed. 59 and 60 accepted, 61 refused, and a refused
declaration leaves **zero** `recurring_item` and **zero** occurrence rows — the
before-the-write ordering works. Leaving `offer_paused_stretch` uncapped is a
defensible call for the reason given.

But the guard was not measuring what its own error message says, in two ways:

**B1 — the cap was walkable.** The guard ran *before* `item.end_date = end_date`,
so it computed against the pre-update end date while `offer_passed_dates` used
the new one. Creating an item with `start=2020-01-01, end=2020-01-15`, then
`PATCH`ing `start_date=2019-12-01, end_date=null`, was **accepted** and wrote
**2437** offered rows against a cap of 60. Reachable from REST and from the MCP
`update_recurring` tool — and the recurring page's edit form always transmits
`end_date`, so this was live on the primary UI path, not a theoretical one.
Fixed by moving the guard below the `end_date` assignment.

**B2 — the cap falsely refused real obligations.** It counted every due date in
the window, including ones already charged. A 5-year monthly obligation with all
61 dates charged could not have its start moved back by one month: refused at
"62 passed dates", when exactly **1** would have been offered. This would have
hit during browser QA on freshly migrated production data, where long-lived
obligations are the norm. Fixed by subtracting `existing_due_dates`.

**Residual, not fixed, your call:** the guard now counts only *newly* offered
dates, so an item with 55 already-pending offers can take 10 more and reach 65
in the dialog. Marginal, and the error message's wording ("would put N passed
dates up for decision") matches the new behaviour. Counting pending + new would
be stricter if you want it.

### Still open, for CP8 rather than for merge

- **The dirty-session leak on a rejected `update_recurring`.** A refused edit
  leaves the item mutated in the session (`session.dirty == True`); I probed it,
  and an unrelated later `commit()` persists `name='RENAMED' amount=999900
  start=2020-01-01`. The API and MCP paths close the session per request so
  nothing corrupts today. The pattern is pre-existing — `update_recurring`
  already had five raise-after-mutation points — but the cap adds a sixth on the
  most likely user error. The fix is to wrap the body in `try/except:
  session.rollback(); raise`, which restores the invariant for all six. I left
  it: restructuring a core function is yours, not a reviewer's, at this gate.
- The two arch-guard indirections (`st = OccurrenceStatus.x; o.status = st`,
  `setattr`) and the missing `architecture:` section in `.engineer/manifest.yml`
  that makes `dae_arch.py` a no-op.
