## Findings

- **The obvious mechanism for AC-24 is broken on this test surface.** Per-item
  isolation via `Session.begin_nested()` is the documented pattern, and
  SQLAlchemy's own SQLite dialect page says SAVEPOINT "fails to participate in
  the enclosing transaction" under the default pysqlite driver — which is
  exactly the driver `db._sqlite_engine` builds and every acceptance test uses.
  It would have been real in Postgres and fake in the tests meant to prove it.
  One commit per charge behaves identically on both engines and matches the unit
  of meaning AC-24 states. Recorded as ADR-0036.

- **Two of the three schema questions dissolved.** W3 (how "ended" differs from
  "switched off") is answered by deriving it from `end_date`, leaving ADR-0005's
  flag meaning only what the user did. W4 (what records the end of a pause) is
  answered by having `restore` write `skipped` occurrences for the dates the
  pause consumed — visible to the user, and it holds in AC-17's own scenario
  where the item is switched off and back on the same day, which any
  "how long was it paused" watermark gets wrong. Neither needs a column.

- **AC-12 needs one enum value, not a table.** `(recurring_id, due_date)` is
  already unique and the engine already skips any date that has an occurrence,
  so an `offered` status is both the offer and the lock. Declining reuses
  `skipped`, which already means "closed, and no run brings it back".

- **AC-9 and AC-12 are separated by a parameter, not by stored state.**
  `create_recurring` takes `declared_on` (default today, not persisted); dates
  before it are offered, dates from it onward are the engine's. The spec's
  Given/When distinction binds straight onto it.

- **The user's constraint changed the module layout.** `services/recurring.py`
  would have gone from 325 to ~520 lines holding catalogue, engine and user
  decisions. It splits into `recurring.py` (catalogue), `occurrences.py` (the
  only module that writes a `RecurringOccurrence`) and `domain/recurrence.py`
  (pure date math extracted from the four-topic grab bag `rules.py`). The
  dependency arrow points one way — `occurrences` takes the item as a parameter
  and never imports the catalogue.

- **One file of feature 006 is touched.** `planned.py`'s two occurrence helpers
  move into `occurrences.py` so the "single writer" invariant is true and
  `arch-check`-able rather than aspirational. AC-27, green today, is the guard.

- **The five APIs the CP3 handlers named by intent now have a shape.**
  `pending_dates` / `accept_pending_dates` / `decline_pending_dates` land in
  `occurrences.py`; `materialize_due` returns a `MaterializationReport` carrying
  `failures`; the movement's origin gets its own `Source` value. Seven handler
  bindings follow the design in F2 and F3, and none of them touches `spec.md`.

- **Carried debt, out of scope here.** W1/I3 from `consistency-check`:
  `feature.md` cites ADR-0013 (superseded by 0026) and its `ADR-020` pointer is
  ambiguous. One-line `feature-edit`; it does not block implementation.
